On Counting Letters

In 1951 a graduate student at MIT was given a choice: sit the final exam, or
write a term paper on finding the most efficient binary code. He chose the
paper, spent months getting nowhere, and was about to give up and study for the
exam when the answer came to him. Instead of building the code from the top
down, splitting the alphabet into halves of nearly equal weight, he built it
from the bottom up. Take the two rarest symbols and join them under a new node
whose weight is their sum. Put that node back among the others and repeat.
When only one node remains, it is the root of a tree, and the path from the
root to each leaf spells out that symbol's code: left is zero, right is one.

The idea is simple enough to state in a paragraph and strong enough that no
prefix code can do better. Frequent symbols end up near the root and get short
codes; rare symbols sink to the bottom and get long ones. Because every symbol
sits at a leaf, no code is the beginning of another, so a decoder reading bits
one at a time always knows when a symbol has ended. Nothing separates the
codes, and nothing needs to.

Consider ordinary English text. The space is the most common character by a
wide margin, followed by e, t, a, o, i and n. A plain eight-bit encoding spends
the same eight bits on a space as on a capital Q or a semicolon. A Huffman code
might spend three bits on the space, four on e, and ten or eleven on the
punctuation that turns up once a page. Over a few thousand characters the
savings add up to something like forty percent.

There is a catch. The decoder has to know the code. One answer is to send the
tree along with the data, but a tree is awkward to write down and easy to get
wrong. A better answer is to notice that the decoder does not need the tree at
all. It needs only the length of each symbol's code. Given the lengths, there
is one natural way to hand out codes: sort the symbols by length, breaking ties
by their value, and count upward in binary, adding a zero bit to the end each
time the length grows. This is called a canonical code. Two programs that agree
on the lengths agree on every code, so a file can store a short list of
lengths in its header and leave the rest to arithmetic.

Canonical codes have another virtue. Within each length the codes are
consecutive numbers. A decoder can read one bit, then two, then three, and at
each step ask a single question: does the number I have read so far fall inside
the range of codes of this length? If it does, the offset into that range picks
out the symbol. If it does not, read another bit. No tree is ever built, no
pointers are chased, and the tables involved fit in a few hundred bytes.

A careful decoder also distrusts its input. A header might claim more codes of
some length than can possibly exist, or a code longer than any the encoder
would produce, or an original size far larger than the data that follows.
Each of these is a different mistake, and each deserves its own error rather
than a crash or a silently wrong answer. The same care applies to the edges:
an empty file has no symbols at all, and a file that repeats one byte has a
tree with a single leaf and no branches, which would give that byte a code of
zero length unless someone remembers to give it one bit.

Huffman's method is more than seventy years old and still sits inside the
formats people use every day. Compressed archives, images and web pages all
lean on it, usually after some other stage has made the data more repetitive.
It is rarely the cleverest part of a modern compressor, but it is almost always
there, quietly counting letters.
