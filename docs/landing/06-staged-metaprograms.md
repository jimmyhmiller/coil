# Porting dossier: explicit staged metaprograms

## Goal

Allow a syntax transform to emit compile-time Coil definitions and explicit
requests to run them in later expansion rounds. This expresses procedural macros
and multi-stage language frontends without an evaluator or a second language.

The protocol is returned `Code`:

```coil
(stage MARKER
  IMPORT...
  (defn phase-entry [(x Code)] (-> Code) ...))

(MARKER phase-entry ARG...)
```

`MARKER` is a fresh symbol chosen by the producing transform. The declaration is
removed from runtime code. The marked request invokes `phase-entry` in the
compiler and is replaced by its returned `Code`. The next expansion round then
continues the source language's normal transforms.

## Why explicit markers matter

A `Code -> Code` function name is not sufficient to identify a staged request:

- the same spelling may be runtime data or a runtime call;
- quoted syntax must remain data;
- a phase entry may be called across modules;
- a later round may add a new entry;
- hygienic code must not accidentally trigger staging.

The fresh marker is an unambiguous capability issued by the transform. Recognition
is based on that marker, while the second element names the requested entry.

## Required semantics

### Isolation

Stage definitions are a separate phase program. They are resolved, checked, and
compiled for metaprogram execution, but never enter the runtime program.

### Cumulative state

Within one compilation, later stage declarations compile with earlier phase
forms. A later entry can call a helper introduced in round one. Definitions may
not be silently reintroduced; the duplicate-stage fixture requires a diagnostic.

### Round behavior

1. A before-expand transform emits a declaration and requests.
2. The compiler splits phase forms from runtime forms.
3. It compiles/adds the phase entries to the in-process meta engine.
4. It expands only requests carrying a known marker.
5. Returned syntax goes into the next ordinary expansion round.
6. The usual transform convergence limit still applies.

### Language resumption

Returned code is not assumed to be final Coil. A Scheme procedural macro may
return Scheme syntax, which must re-enter Scheme lowering. This is why stage
execution cannot be bolted onto the end of the compiler pipeline.

### Cross-module routing

The declaration and request may be in different modules. The marker/entry table
is compilation-scoped, not tied to adjacency in one source file.

## Implementation anatomy

Most generic implementation lives in `src/compiler/expander.coil`:

- stage declaration recognition and validation;
- splitting phase/runtime forms;
- cumulative phase-form storage;
- isolated load/resolve/check;
- additive installation into the existing meta engine;
- marker-aware tree traversal that skips quotes;
- invocation recursion/convergence guards;
- copying signatures needed during continued expansion.

Supporting changes touch `comptime.coil`, `metaengine.coil`, `check.coil`, and
`parser.coil` as the phase program becomes more independent. Scheme dialect
changes demonstrate language resumption but should not define the generic
protocol.

The definitive generic fixtures are:

- `generated_stage*.coil`;
- `isolated_stage*.coil`;
- `multiround_stage*.coil`;
- `duplicate_stage_test.coil`;
- `cross_module_stage*.coil`.

Sprout is a later explanatory consumer, not a prerequisite.

## Extraction strategy

Port this as a sequence, leaving the compiler green after every step:

1. Parse and remove explicit stage declarations; compile one generated entry.
2. Isolate phase forms from runtime output.
3. Route explicit marked requests and ignore identical unmarked/quoted syntax.
4. Return stage results to ordinary expansion.
5. Preserve cumulative phase source across rounds.
6. Reject duplicate definitions and unavailable entries precisely.
7. Prove cross-module requests.
8. Make imported phase dependencies pass through normal expansion.
9. Add disposable stage-compilation arenas only after semantics are stable; arena
   ownership is a separate change.

Do not port linked `Code` lists, destructive rewriting, Scheme procedural syntax,
or Jolt compatibility as prerequisites.

## Known gaps and risks

- Current implementation is concentrated in a very large expander function and
  was developed alongside arena experiments. Separate semantic state from memory
  ownership before extraction.
- Define exact visibility/redefinition rules for phase bindings. “Cumulative”
  must not mean accidental shadowing.
- Error diagnostics need source attribution for both the declaration and request.
- A stage result that emits another stage needs a bounded, observable rule.
- Imported phase modules may themselves contain macros; normal expansion parity
  must be demonstrated without Scheme.
- Hygiene/context preservation across Code boxing, invocation, and reinsertion
  needs identity tests.
- Stage compilation should eventually have a disposable arena and self-owning
  engine image, but premature freeing previously created dangling registries.
- Target behavior must be defined for interpreter and Wasm engines, not just the
  host-native JIT.

## Acceptance

- All five generic fixture families pass.
- Quoted marker-shaped data never executes.
- An unmarked call with the same entry name remains ordinary code.
- Phase definitions are absent from emitted runtime IR/object symbols.
- Later rounds reuse earlier helpers and reject redefinition.
- Cross-module requests work independent of source adjacency.
- Returned syntax resumes the producing language's transforms.
- Stage2/stage3 bootstrap reaches a fixpoint.
- Peak stage memory is measured separately, but semantic acceptance does not
  depend on the unfinished Jolt memory target.
