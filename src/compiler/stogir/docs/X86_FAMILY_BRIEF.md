# Working on an x86-64 operation family

Common rules for everyone filling in a family of the x86-64 backend. Your own
assignment (which family, which tests) comes separately.

## Read first
1. `docs/X86_PORT.md`: design decisions. Follow them; if you must change or
   add one, edit that file in the same commit and say so in your report.
2. `docs/X86_FAMILIES.md`: the extension points (`select!`, `constrain!`,
   `emit!`, how a family claims nodes in `x64/families.coil`).
3. Your family's placeholder module header in `src/stogir/x64/`.
4. The AArch64 implementation of the same family in `src/stogir/a64/` as the
   model for behavior, representation invariants and edge cases; the relevant
   section of `docs/x86-maps/calls-frames-operations.md` (it lists, per file,
   the natural x86-64 equivalents and where the SSE2 baseline bites).
5. Upstream's x86 code for the same operations in
   `/Users/jimmyhmiller/Documents/Code/open-source/ir/ir_x86.dasc`.
6. `src/stogir/x64/encode.coil` header for the encoder conventions. If an
   instruction form you need is missing, add it there with byte-exact cases in
   `tests/x64-encode.coil` generated by `tools/x86/gen-encode-cases.py`
   (never hand-derived bytes).

## Where to work
- Create your own worktree and branch from `feature/x86`:
  `cd /Users/jimmyhmiller/Documents/Code/projects/coil-stogir && git worktree add -b x86/NAME .worktrees/x86-NAME feature/x86 && mkdir -p .worktrees/x86-NAME/build`
  Work only there. Commit as you go with plain messages (no Co-Authored-By or
  "Generated with" trailers). Never `git stash`. Do not push.
- Other families are being implemented at the same time in other worktrees.
  Stay inside your family's modules. When you need a change in a core file
  (`function`, `match`, `select`, `emit`, `constraints`, `allocate`,
  `transfers`, `value`, `families`, `incoming`, `fixups`, `compile`) keep it
  small and local, and list every such change in your report so merges are
  easy. Before your final report, merge the current `feature/x86` into your
  branch (`git merge feature/x86`), resolve conflicts, and re-run your gate.

## Hosts
- Linux x86-64: `tools/x86/remote-test.sh tests/NAME.coil ...` from your
  worktree (rsync + run with the Linux compiler; `JOBS=N` to change
  parallelism; logs under `~/stogir-x86/wt/<worktree-name>/build/logs` on the
  host). `ssh computer.jimmyhmiller.com` for gdb and objdump
  (`objdump -D -b binary -mi386:x86-64 FILE` for raw text dumped by a test).
- Mac arm64 (anything neutral or under `a64/` that you touch must still pass
  here): `COIL_LIBRARY_STATE=0 /Users/jimmyhmiller/Documents/Code/projects/coil/.worktrees/stogir-idiom-edges/build/bin/coil-candidate run tests/NAME.coil --backend stogir -O3 --no-debug --debug-checks`

## Rules
- Correct first. No hacks, no silent fallbacks: what you do not implement
  returns a clear `Err`. Never emit code you have not tested.
- Baseline CPU is SSE2 x86-64. Instructions beyond it (POPCNT, LZCNT, BMI,
  SSE4.1, AVX, FMA) are not used.
- Flags: nothing emitted between a flag producer and its consumer may write
  flags (see `X86_PORT.md`). Scratch registers are r10, r11, xmm14, xmm15.
- Fixed registers (rcx for counts, rax/rdx for multiply/divide, rax for
  cmpxchg) are expressed as clobbers with copies in, as the core does for
  shifts and division (see `X86_PORT.md`, "Fixed registers are clobbers").
- Integer division traps on zero and on MIN / -1, as LLVM-built code does.
- Tests are the gate:
  - The existing target-neutral tests of your family
    (`tools/x86/family-tests.sh FAMILY`, see `tests/X64_STATUS.md`) must pass
    on Linux, unchanged in what they check. Where a test asserts something
    that is AArch64-specific (instruction shapes, byte sizes, a convention
    number, AArch64 results for undefined inputs), guard only that assertion
    with `(target/arch-pick A64-FORM X64-FORM)` and give x64 its own correct
    expectation; list each such edit in your report.
  - Add `tests/x64-FAMILY-*.coil` tests for x86-specific hazards (aliasing of
    two-address operands, fixed-register conflicts, flag liveness, every
    width, boundary immediates, register pressure and spilled operands).
  - Add your operations to a seeded differential stress test (see
    `tests/x64-core-stress.coil` and `x64/testing.coil`) where a reference
    evaluator is practical.
  - Re-run `tests/x64-core-*.coil` before reporting; they must still pass.
- Report confirmed bugs in the Coil compiler itself (not your code) in the
  `coil-bugs` pad, following the instructions in that pad.

## Final report (under 450 words)
What works; files and line counts; core files touched and why; tests passing
on Linux (counts, and the family tests still failing with the reason for
each); test edits made for target-specific expectations; what is left
unimplemented (each a hard error); code-quality gaps worth tuning later; the
commit hash after merging `feature/x86`.
